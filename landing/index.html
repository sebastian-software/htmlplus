The gap in HTML forms

Native forms handle naming, submission, validation, labels, disabling, and reset. Then a project needs a tag field or a bank account number, and that work moves into framework code: hidden inputs, value syncing, and a separate validation path.

html+ keeps the native contract for those fields. Each one has a name, appears in FormData, blocks an invalid submission, follows a disabled fieldset, and returns to its default on reset. Where a native control already does the job, keep using it.

Where a component stops

A component knows the rules of its value and interaction. It never fetches your records or starts your workflows.

You write ordinary markup

Build the project, load one module, and use the elements inside a normal form. Labels, required, and FormData work as they do for native fields.

<script type="module" src="/dist/src/index.js"></script>

<form>
  <label for="account">IBAN</label>
  <h6-iban id="account" name="iban" required></h6-iban>

  <label for="topics">Topics</label>
  <h6-tags id="topics" name="topics"></h6-tags>

  <button>Submit</button>
</form>

Each element brings a neutral base appearance. Restyle it with inherited --hp-* tokens and CSS parts, in plain CSS or on top of a shadcn palette.

Where the project stands

html+ is a working prototype. All twenty-four elements run through browser checks in Chromium, Firefox, and WebKit on every change, but some things are not done yet:

  • There is no npm package. To try it, clone the repository and build it.
  • Element names may still change, because the h6- prefix is provisional.
  • Most elements need JavaScript. Server-side rendering is not implemented.
  • Screen reader combinations and password manager autofill on real devices have not been checked by hand.

The code is open source under the Apache License 2.0. The README covers installation and browser support, and the project plan lists what comes next.
